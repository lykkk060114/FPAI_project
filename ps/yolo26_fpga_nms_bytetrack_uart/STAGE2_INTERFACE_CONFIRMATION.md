# FPGA 前处理开发要求与接口答复（以当前 NPU 为准）

核对日期：2026-10-13。依据：本地实际模型、官方 SDK 源码、SSH 板端只读寄存器。未修改寄存器、BOOT 或启动程序。

## 一、我们要求实现什么

本阶段固定使用现有 YOLO26 模型，要求 FPGA 输出 **宽640、高352** 的检测图像。采用最容易与现有程序兼容的方案：**中心裁剪＋3倍整数采样**，不做补边，不改成640×640，不重新转换模型。

具体做法：1920×1080原图去掉顶部12行和底部12行，剩下1920×1056，再横向和纵向每3个像素取一个，得到640×352。画面比例不变，只损失上下很小的区域。

现有官方硬件已经有这项功能。对方的任务是核实并复用它、保证新增模块接对支路、保持颜色精度和传输协议，并通过仿真及上板验收。不要为了新增模块再做一次缩放。

当前存在两个图像支路，不能把 PS 全分辨率显示缓存当作 NPU 输入：

```text
SDI 1920×1080
 ├─ PS resize，步长1 → RGB565 → PS DDR四缓冲 → 分类裁剪/绘制 → HDMI
 └─ PL resize，步长3，裁剪上下各12行 → 640×352 → ImageMake/PLDDR → ZG330
                                                        ↓
                                 PS 六路输出解码 → ByteTrack → UART
```

Stage 1 自定义位流是否已经加载、模块实际接在哪条支路，本次没有证据确认；须以队友 RTL 和启动介质为准。

## 二、对方清单的问题，直接答复

**1. FPGA目前输出多大？** 检测支路640×352；PS原图支路1920×1080。两条支路作用不同。

**2. PS怎样接收？** 原图以RGB565格式写入PS DDR，2字节/像素，3840字节/行，4147200字节/帧，四缓冲轮换；程序轮询完成位。检测图像走现有ImageMake和PLDDR接口送NPU，不要求CPU先读取原图再缩放。

**3. NPU需要什么？** 空间尺寸固定640×352，三通道；FPGA沿用官方8bit像素接口，后续数据排列和模型输入处理沿用SDK。模型逻辑Tensor是FP32 NHWC，不能据此要求RTL直接发普通FP32数组。RGB/BGR线序需用彩条核对，核对前不要擅自交换。

**4. PS还在做检测前处理吗？** 当前采集检测路径不执行CPU Resize或Letterbox。CPU上分类器的目标裁剪和224×224缩放是另一项工作，本阶段继续保留。

**5. write_ps_size是什么？** 寄存器06c表示8字节传输单位数，当前518400，对应4147200字节。07c在SDK的YUV422分支写入像素宽度；当前RGB565分支不写，不能拿它的0判断图像宽度。

**6. 相机60Hz为什么只有约30FPS？** 输入帧率与检测速度不同；历史NPU每帧约30ms。YAML的fps字段不配置相机实际输出时序。新RTL按相机实际输入时序工作，模型处理不过来时必须遵守原有取帧机制，不能拼接两帧。

## 三、寄存器依据

|---|---|---|
| 020 | 00000003 | 水平采样步长3 |
| 024 | 00000003 | 垂直采样步长3 |
| 028 | 00000000 | x0=0 |
| 02c | 0000000c | y0=12 |
| 030 | 0000077f | x1=1919，含末端 |
| 034 | 0000042b | y1=1067，含末端 |
| 038 | 00000780 | 相机宽1920 |
| 03c | 00000438 | 相机高1080 |
| 05c | 0000077f | PS x0高16位、x1低16位：0～1919 |
| 060 | 00000437 | PS y0高16位、y1低16位：0～1079 |
| 064 | 07800438 | 相机宽高：1920×1080 |
| 068 | 00000011 | 水平步长高半字节1、垂直步长低半字节1 |
| 06c | 0007e900 | 518400个8字节传输单位，即4147200字节 |
| 07c | 00000000 | 当前RGB565路径未设置；不能解释为当前输出宽度0 |

配置源码位于 `/home/lykkk/FPAI/fpai_demo_package_26040701/deps/modelzoo_utils/include/`：

- `et_device.hpp:791`：`hardResizePL()` 写020～03c。
- `et_device.hpp:703`：`hardResizePS()` 写05c～06c；仅YUV422分支把FRAME_WIDTH写入07c。因此07c在该分支的单位是像素，RTL其余用途未知。
- `pipeline/io/input/sdicamera.hpp:77`：`resizePL()` 根据相机尺寸/网络尺寸取整数商并计算裁剪；初始化时配置，不自动探测相机分辨率或帧率。

当前裁剪1920×1056，再按3采样，输出640×352。本阶段保持该配置。

## P0-2 PS接收接口

| 项目 | 当前实现 |
|---|---|
| 分辨率/格式 | 1920×1080 RGB565，每像素2字节 |
| 行大小/帧大小 | 紧密排列3840字节/行，4147200字节/帧 |
| 缓冲 | u-dma-buf管理的PS DDR，4个帧槽，由actor轮换 |
| 提交 | `SDICamera::take()` 将物理地址右移3写到050，再向取帧寄存器写1 |
| 完成 | `wait()`轮询058：bit0完成，bit2错误，默认100ms超时；不是CPU接收完成中断 |
| SOF/tuser/TLAST | PS代码未说明，须检查RTL，不猜测 |

历史成功日志中的四个PS地址为31100000、314f4800、318e9000、31cdd800；地址由分配决定，不能硬编码。当前058=1只是保留状态，不能证明相机现在正常。

检测支路没有CPU Resize/Letterbox；分类器仍在CPU上裁剪目标并缩放到224×224。HDMI绘制使用RGB565 PS帧。

**必须保留PS原图支路。** PS显示帧继续为1920×1080 RGB565，缓冲继续为4147200字节；不要因为检测输入为640×352就修改显示和分类原图尺寸。

## P0-3 模型和预处理

模型：`imodel/ZG/yolo26_panda_conv_ZG.json/.raw`，iCraft 3.36.1，ZG330。

- 原ONNX输入：FP32 NCHW `[1,3,352,640]`，RGB，0～1（验证脚本转换RGB并除255）。
- iCraft完整图入口：UINT8 NHWC动态形状；Host Resize op1目标`[1,352,640,3]`，INTER_LINEAR。
- 板端`view_except_op_ids: [0,1]`跳过上述Host入口/Resize，因此它们不代表板端正在执行的软件缩放。
- 实际首个NPU HardOp的逻辑输入：FP32 NHWC `[1,352,640,3]`，之后有Cast和编译后的输入处理；不是可以直接按普通UINT8数组解释的Tensor。
- SDK `sdicamera_input_actor.hpp:197`调用`runImageMakeForward(...,8,false,0)`；ImageMake为8bit、3通道数据搬运/排列，使用NPU backend的内存映射构建Tensor。**物理排列、FP32逻辑视图和通道交换须联合核对，不能把RGB888线性字节直接当FP32输入。**
- 转换链使用BGR图像入口（验证脚本`validation_sim_bgr_input`）；原ONNX为RGB。RTL输出线序与SDK最终RGB/BGR转换是否完全一致，需要彩条/真实帧对照验收。
- 当前PL路径无padding，无Letterbox；图中的INTER_LINEAR Host Resize已被跳过。板端现有采样方式和离线验证脚本的Letterbox也不一致。
- scale/zero-point不能用一个通用INT8参数代替：当前模型有FP32/TF32/BF16编译值，具体输入处理由JSON/RAW生成。尚未逐项解析其数值，标记为待核对。

## 四、FPGA队友需要完成的工作

### 1. 先确认模块接在哪里

提供实际RTL连接图，标清SDI接收、检测resize、PS原图传输、ImageMake入口以及新增video_preprocess的位置。确认新增模块是否同时影响两条支路。

检测支路必须保留每通道8bit精度。Stage 1的RGB888→RGB565→24bit量化不得串在检测支路中；若保留该模块，检测支路旁路量化。显示支路继续使用原有RGB565接口。

如果SDI前级已经输出RGB888，直接复用，不重复做颜色转换。

### 2. 固定裁剪和采样要求

- 原图尺寸：1920×1080。
- 裁剪区域：x=0～1919，y=12～1067，末端包含在内。
- 水平/垂直采样步长：3/3。
- 输出尺寸：640×352，每帧225280个有效像素，三通道各8bit。
- 不添加padding，不做第二次resize，不在RTL中除255或加mean/std。

优先复用现有cmos_resize_24bit和寄存器配置。核对现有模块的采样相位：候选软件参考为 `out[y,x] = in[12+3*y,3*x]`；必须结合RTL或dump确认现有模块是否采用该索引。若相位不同，先记录并与PS侧统一，再定逐像素参考，不能只看输出尺寸一致。

### 3. 保持官方传输接口

保留现有ImageMake/PLDDR数据排列和NPU入口连接，不新增“CPU取图再转交NPU”的中间步骤。像素流是8bit三通道，Tensor逻辑视图由SDK负责。

提供实际通道在线上的位定义，例如R/G/B各对应哪8位，并用红、绿、蓝彩条核对实际NPU输入dump。图像源是RGB还是BGR以联调证据确定，不凭模块名字判断。

保留PS原图DMA、四缓冲、058完成/错误位及现有寄存器映射。物理地址由软件分配，不在RTL中固定此前日志中的缓冲地址。

明确帧首、行尾、有效像素和ready/valid握手的实际协议。接口若不是AXI Stream，按现有接口说明，不强行新增tuser/TLAST。背压时不得丢有效像素；丢帧必须整帧丢弃并记录，不能混帧。跨时钟域沿用正确的同步/FIFO机制。

### 4. 做仿真，交出图像而不是只交BOOT

先用坐标图案和RGB彩条测试：验证裁剪边界、3倍采样、640×352像素计数、颜色线序、帧切换和背压。根据确认后的采样规则，与CPU参考逐像素比较，要求像素完全一致。

再综合和实现，提交时序结果、资源增量、RTL版本及BOOT SHA-256。新增模块先完成Stage 1上板验证，再验证整个检测支路。

### 5. 上板验收

我们配合PS采集和NPU验证，对方提供匹配的位流及RTL接口说明：

1. 保存1920×1080 RGB565原图和640×352检测入口图，各说明捕获位置；普通ImageMake图像dump不等同于FP32 Tensor原始字节。
2. 用静态测试图比较修改前后像素；用真实相机确认无错行、混帧、颜色交换或重复缩放。
3. 连续至少100次取帧无100ms超时，错误位不置位；记录运行时间、实际有效帧率及整帧丢弃数量。
4. 运行现有YOLO26，核对检测框映射回原图：沿用 `x原图=3*x检测图`、`y原图=3*y检测图+12`，再裁到边界。
5. 确认原有HDMI、分类裁剪、ByteTrack和UART路径未因帧格式变化失效。

### 6. 最终交付清单

- 实际RTL连接图、修改过的RTL及明确的旁路配置。
- 寄存器、颜色位定义、帧/行握手协议说明。
- 仿真和CPU逐像素比较结果。
- 综合/时序/资源结果、BOOT文件及SHA-256。
- 两个支路的图像、连续取帧日志、检测联调结果。

PS侧负责保持现有模型和配置、抓取图像、核对模型输入以及解码坐标；FPGA侧负责图像采样、颜色精度、硬件传输协议和位流正确性。
